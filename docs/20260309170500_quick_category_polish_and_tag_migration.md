## 1. Multi-Tagging System Migration
One of the most critical structural changes in this phase was the transition from a legacy single-tag model to a flexible multi-tagging system.

### The Problem
Previously, transactions were limited to a single `tagId`. This restricted users from categorizing a single transaction across multiple dimensions (e.g., a "Food" expense that is also "Business Related" and "Recurring").

### The Solution: `tagNames` Architecture
We migrated the `Expense` schema and `ExpenseRepository` to support an array of tags.
- **Implementation**: The database now stores/retrieves an array of tag strings.
- **Benefit**: Allows complex filtering and more accurate budget tracking.
- **Future Dev Note**: Ensure that any new ingestion logic (SMS or Voice) correctly maps detected keywords into this array rather than overwriting a single ID.

## 2. QuickCategoryScreen Stability & Logic
The `QuickCategoryScreen` (triggered from M-Pesa notifications) was optimized for production-grade reliability.

### Cold Start Initialization
- **Problem**: When the app was offline and launched via a notification action, it would often error with "Database not initialized".
- **Fix**: Implemented explicit `await Database.init()` within the screen's lifecycle. This ensures the SQLite connection is established before the repository attempts to fetch transaction data.

### End-to-End Ingestion Flow
The flow is now fully autonomous:
1. **SMS Arrival**: Detected by the native Android `SmsListenerModule`.
2. **Ingestion**: `IngestionService` parses the message and auto-assigns a category.
3. **Notification**: User receives a high-importance notification.
4. **Action**: User can "Confirm" (verifies DB entry) or "Change" (launches the polished Grid UI).

## 4. Robust Database Backup & Restore Flow
To ensure data portability and safety, a symmetric, transaction-based backup system was implemented.

### Complete Dynamic Export
- **Discovery**: Uses `sqlite_master` to query all user-defined tables, automatically including new features (Budgets, Goals, etc.) without manual schema updates.
- **Format**: V2-JSON structure stores table data in a name-to-rows map, preserving all metadata including `transactionId` and `isVerified` flags.

### Symmetric Restore Integrity
- **Atomicity**: Wrapped in a single SQLite transaction (`BEGIN TRANSACTION` / `COMMIT`). If any individual table data is corrupt, the entire restore is rolled back to protect the existing database.
- **Foreign Key Management**: Temporarily relaxes constraints (`PRAGMA foreign_keys = OFF`) to allow a clean wipe-and-reload of interrelated data without throwing dependency errors.
- **Smart Catch-Up Logic**: Post-restore, the app automatically triggers an `IngestionService.runCatchUpScan()`. This scans for M-Pesa SMS messages received *after* the backup was created but *before* the restore occurred, ensuring no transactions are lost during the transition.
